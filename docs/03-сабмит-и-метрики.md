# Сабмит и метрики

## Формат ответа

CSV или parquet с заголовком. Обязательны две колонки, ещё две опциональны:

```
fragment_id,soh_pred
a1b2c3d4e5f60718,0.9412
b2c3d4e5f6071829,0.8875
c3d4e5f607182930,0.9021
```

Если хотите участвовать в номинации «калибровка», добавьте границы 90 %
интервала — но тогда их надо заполнить **во всех строках**:

```
fragment_id,soh_pred,soh_lo,soh_hi
a1b2c3d4e5f60718,0.9412,0.9130,0.9680
b2c3d4e5f6071829,0.8875,0.8610,0.9140
c3d4e5f607182930,0.9021,0.8800,0.9250
```

| колонка | обязательна | что это |
|---|---|---|
| `fragment_id` | да | идентификатор из тестового файла |
| `soh_pred` | да | ваш прогноз SOH |
| `soh_lo`, `soh_hi` | нет | границы 90 % интервала; нужны для номинации «калибровка» |

Готовые примеры: [`submission_example.csv`](../examples/submission_example.csv)
(минимальный) и
[`submission_with_intervals.csv`](../examples/submission_with_intervals.csv)
(с интервалами). Идентификаторы в них выдуманы, поэтому валидатор скажет, что
таких фрагментов в тесте нет, — примеры показывают **формат**, а не готовый
ответ.

### Отправка через pull request

Команда отправляет один pull request и обновляет его при новых версиях сабмита.
Положите в `submissions/<team-slug>/`:

- `submission.csv` — CSV с предсказаниями; именно этот файл оценивается;
- `README.md` — описание подхода и команда для воспроизведения обучения;
- исходный код обучения и зафиксированные зависимости.

После каждого обновления PR проверяется CSV и пересчитывается официальный балл.
Результат проверки появится в PR, а лидерборд покажет последнюю оценку команды.

Код нужен для ревью и воспроизводимости. Официальный оценщик читает только
`submission.csv` и не запускает код из PR. Подготовьте файл локально по открытым
train/validation/test parquet и проверьте его перед отправкой:

```bash
uv run bsb validate --submission submissions/<team-slug>/submission.csv
```

## Настройка оценщика (организаторам)

Workflow `.github/workflows/score-submissions.yml` реагирует на открытие,
обновление и закрытие PR в `main`. Он берёт CSV из head PR через публичный raw
endpoint, валидирует его и пересчитывает оценки открытых PR.
Код из PR не checkout’ится и не запускается. Результат обновляется в комментарии
к PR и в автоматически создаваемой issue «Лидерборд battery-soh-bench». Проверка
текущего PR завершается ошибкой, если его CSV невалиден.

Чтобы дать доверенному workflow доступ к закрытой разметке, один раз на машине
организатора выполните:

```bash
uv run python scripts/export_eval_truth.py
gh secret set BSB_TEST_TRUTH_B85 < data/private/test_truth.b85
```

Сгенерированный файл содержит закрытые метки и исключён Git-правилом `data/*`;
не добавляйте его в коммит. Workflow получает данные только из секрета
`BSB_TEST_TRUTH_B85`. У репозитория также должны быть включены GitHub Actions и
право `issues: write` для `GITHUB_TOKEN` — минимальные разрешения объявлены в
workflow.

`pull_request_target` нужен, чтобы workflow и оценщик брались из доверенной
базовой ветки, а не из PR. Workflow ограничен `main`, не использует файлы PR
как исполняемый код и принимает оттуда только `submission.csv`. Для публичных
репозиториев GitHub планирует с 2 ноября 2026 года блокировать
`pull_request_target` по умолчанию; администратору репозитория или организации
нужно явно разрешить этот event в Actions workflow execution policy ([инструкция GitHub](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)).

### Правила, которые проверяет валидатор

```bash
uv run bsb validate --submission submission.csv
```

1. **Полнота.** Все `fragment_id` из тестового файла должны быть в сабмите, и
   лишних быть не должно. Пропуск хотя бы одной строки — ошибка.
2. **Диапазон.** `soh_pred` должен лежать в `(0, 1.2]`.
3. **Числа.** Никаких пустых значений и `NaN`.
4. **Уникальность.** Один `fragment_id` — одна строка.
5. **Согласованность интервалов** (если они заданы):
   `soh_lo <= soh_pred <= soh_hi`. Задавать нужно **обе** колонки или ни одной.

Сообщения об ошибках указывают конкретные строки — чтобы не выяснять формат
перепиской.

## Как считаются результаты

Две основные величины:

- **MAE** — средняя абсолютная ошибка, в процентных пунктах SOH. Ошибка 4 п.п.
  означает, что вы в среднем промахиваетесь на 0.04 по шкале SOH.
- **P95** — 95-й процентиль абсолютной ошибки. Это «худший случай»: он важен,
  потому что в реальной системе управления батареей редкие грубые промахи
  опаснее, чем стабильная небольшая неточность.

Плюс разбивки: по химии, по температуре и по децилям SOH. Последняя особенно
интересна — сильно состаренных ячеек всегда меньше, и именно на них модели чаще
всего разваливаются.

```bash
uv run bsb eval --submission submission.csv                    # основная номинация
uv run bsb eval --submission submission.csv --hard-mode        # бонусная LFP
```

## Номинации

| номинация | что считается | как попасть |
|---|---|---|
| **основная** | NCA + NMC | по умолчанию |
| **LFP (бонусная)** | только LFP | тот же сабмит, считается с `--hard-mode` |
| **калибровка** | покрытие 90 % интервала и его средняя ширина | добавить `soh_lo` и `soh_hi` |
| **экономность** | размер модели в байтах и минимальная ширина окна `delta_v`, при которой держится точность | см. §10 ТЗ |

Основная номинация и LFP считаются **по одному и тому же сабмиту** — отдельно
сдавать ничего не нужно.

Почему LFP отдельно: LFP заметно труднее (у него плоское плато, и окно 0.2 В
даёт мало информации), поэтому его результат не должен топить команду в основной
номинации. Подробности — §9 ТЗ.

## С чего начать

1. Поставить окружение: см. [Установку в README](../README.md#установка).
2. Получить данные и фрагменты: [02-задача-и-данные.md](02-задача-и-данные.md).
3. Посмотреть ориентиры — что уже даёт бейзлайн и какой результат считается
   хорошим: [04-ориентиры.md](04-ориентиры.md).
4. Собрать свой сабмит и проверить его валидатором.

Бейзлайн можно посчитать прямо из тулкита:

```bash
uv run bsb baseline --model elastic_net        # и получить готовый сабмит
uv run bsb baseline --model constant           # «пол» — хуже него быть нельзя
```
