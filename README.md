# battery-soh-bench

Тулкит студенческого соревнования: по случайному фрагменту зарядной кривой
фиксированной ширины по напряжению предсказать нормированную остаточную
ёмкость (SOH) литий-ионной ячейки на момент этого цикла.

Обучение — CALCE, KIT NMC/C-SiO, Oxford. Скрытый тест — Sandia (NCA + NMC;
LFP — отдельная бонусная номинация).

Техническое задание — [battery-soh-bench-spec.md](battery-soh-bench-spec.md).
Он же единственный источник правды по решениям; ссылки вида «§5.1» ниже —
на его разделы.

## Установка

```bash
git clone <repo> && cd battery-soh-bench
python3.11 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
bsb config-check
```

Данные в репозиторий не входят (ТЗ §3). Скачайте их скриптами из `scripts/`,
затем выполните `scripts/prepare_all.sh`.

### Источник теста: SNL через BatteryLife

§17.4 предполагал Battery Archive. Программного доступа там нет, а массовая
выгрузка — только по письму, поэтому тест берётся из **BatteryLife** (KDD 2025),
открытого сводного датасета на Zenodo под CC-BY-4.0
(`scripts/download_sandia.sh`, sha256 зафиксирован). Это тот же SNL: те же ID
ячеек `SNL_18650_*`, тот же протокол (заряд 0.5C у всех), те же три химии.

| | |
|---|---|
| ячеек в источнике | 61 (NCA 22, NMC 21, LFP 18) |
| в бенчмарке | **57**: исключены 4 ячейки окна 20-80 % SOC |
| температуры | 15 / 25 / 35 °C |
| опорных циклов | 7034 (медиана 37 на ячейку) |
| дискретизация | 10 с в начале жизни, до 120 с в конце |

Отличия от §17.4, которые надо держать в голове:

* **61 ячейка вместо 86** — BatteryLife публикует те, для которых есть метки
  ресурса; группа 40-60 % SOC не попала. Для нас это скорее выигрыш: там заряд
  шёл CC по ёмкостным лимитам, то есть протокол зависел от DOD, а §5.1 требует
  единообразия;
* **4 ячейки окна 20-80 % исключены**: в подмножестве у них нет ни одного
  полного 0-100 % цикла (размах 2.700-3.980 В при границах 2.5-4.2 В), поэтому
  capacity check определить нечем, а ёмкость окна 20-80 — это другая величина,
  а не SOH полной ячейки;
* **файлы покрывают разные окна жизни**: у NMC_15C реплика `b` начинается там,
  где `a` уже закончилась (2.015 против 2.724 А·ч). Это объясняет «ступеньки»
  на графиках, которые не являются ошибкой разметки;
* **у 8 ячеек с режимом 0.5-0.5C** рабочий цикл неотличим от capacity check,
  поэтому опорными становятся все полные циклы (474-3050 на ячейку). Это
  записано как открытый вопрос: можно оставить только проверки на границах
  раундов (группы по три цикла), но тогда ячеек с богатой траекторией не будет.

Атрибуция обязательна тройная: BatteryLife, Battery Archive и Preger et al.

### Открытый вопрос по таргету CALCE (тип 3)

У CS2 тип 3 (`CS2_3`, `CS2_9`) меняет ток разряда каждый цикл: 0.11, 0.22,
0.55, 1.1, 1.65, 2.2 А. Ёмкость зависит от тока — **1.098 А·ч при 0.11 А против
0.830 А·ч при 2.2 А**, — а `soh` считается от разрядной ёмкости. Соседние циклы
поэтому скачут на 25% по режиму, а не по старению, и кривая SOH (график §14)
перестаёт быть монотонной: `reports/acceptance_calce.png`.

Механизм фильтра написан (`labels.reference_cycle_rules.calce.
require_modal_discharge_current`), но по умолчанию **выключен**: наивное «оставить
модальный ток» ломается на типах 5-6 (полные циклы редки и идут другим током —
ячейка остаётся без `bol`) и на типе 3 сдвигает первый опорный цикл, давая
`soh > 1.2`. Нужно решение владельца (§5): исключить тип 3, считать `bol` по
отфильтрованным циклам или нормировать ёмкость на ток разряда.

### Вторая причина: «полный» цикл на самом деле не заряжался

Кривые немонотонны у **всех** 14 ячеек, и причина не только в типе 3. Диагностика
`calce_CS2_33` (862 опорных цикла):

* первые 20 циклов идут гладко: 1.160 → 1.136 А·ч;
* 162 цикла имеют ёмкость < 0.5·bol, и все они лежат в циклах 639-866, то есть
  в конце жизни;
* у этих циклов медианный **заряд** равен 0.119 А·ч против 0.886 А·ч у остальных,
  но напряжение всё равно доходит до 4.201 В и разряд до 2.700 В.

То есть правило «полный цикл = дошёл по напряжению до верха и до низа» пропускает
циклы, где ячейка была уже почти полной и заряд перенёс всего 0.12 А·ч. Их
разрядная ёмкость занижена в разы, и именно они дают «восстановления» SOH.

Механическое следствие: опорный цикл должен переносить существенный заряд, а не
только достигать границ по напряжению. Порог (например, `charge_ah >= 0.5·bol`)
— это правило §5, поэтому оно ждёт вашего решения, а не выбрано мной.

Тот же вопрос стоит и между датасетами: Oxford разряжается на C/18.5, CALCE —
на 0.5C или 1C, Sandia — на 0.5C. Это систематический сдвиг в **таргете**, а не
во входе.

### Уточнение к §6 ТЗ

ТЗ §6 предполагает, что `load_cell` сразу возвращает `CellBundle` по схеме §4.
Это невозможно без подлога: `cells.bol_capacity_ah` и `cycles.soh` выводятся из
опорных циклов, а какие циклы опорные — определяется правилом, которое
применяется следующим шагом. Поэтому адаптеры возвращают промежуточный
`RawBundle` (ёмкость и timeseries как в исходнике) и уже из него
`mark_reference_cycles` через `bsb.labels.build_labels` собирает §4. Так ни одно
производное поле не заполняется «чем-нибудь похожим».
